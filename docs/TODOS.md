# Project TODOs and Future Enhancements

This document outlines planned features, potential improvements, and known limitations for the Halal Random Strings project. Contributions are welcome for any of these items!

## Completed Features

*   **String length control:** `min_words` and `max_words` CLI flags and API options for fine-grained word count bounds.
*   **Custom separator support:** Full CLI (`-sep`) and engine (`Options.Sep`) support for arbitrary delimiters (e.g. `_`, `.`, `-`).
*   **D1 schema verification and safe batching:** Automated table checks, non-interactive execution, and `INSERT OR IGNORE` batching in `populate_d1.py`.
*   **Category filtering and single-category fallback:** Validated multi-category and single-category string generation.
*   **Thread-safe embedded dictionary engine:** `Engine` architecture supporting embedded `words.json` and custom runtime overrides with full race safety.

## High Priority

*   **Refine `words.json` categories and rules:** Continuously review and improve the categorization of words and the rules for combining them to ensure more meaningful and diverse string generation.
*   **Implement more sophisticated word combination logic:** Explore algorithms that can generate more grammatically correct or contextually relevant multi-word strings beyond simple concatenation.
*   **Add more comprehensive word lists:** Expand all existing categories with more words, especially for less populated ones, and introduce new relevant categories as needed.

## Medium Priority

*   **Add API Key/Authentication to Cloudflare Worker:** Secure the API endpoints to prevent unauthorized access.
*   **Web UI for string generation:** Create a lightweight web interface for users to generate strings interactively.
*   **Internationalization (I18n):** Explore supporting word lists in other languages.

## Known Limitations

*   **Current word combination is pattern-based:** Strings are generated by combining words from selected categories according to declarative rules.
*   **No built-in string expiration/cleanup:** The D1 schema includes `used_at` and `used_by` fields, but there's no automated background worker to expire or clean up old/unused strings.
